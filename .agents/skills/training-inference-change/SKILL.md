# 训练与推理变更

先读取目标项目指令、需求依据、相关实现与已有失败材料，选择本次适用参考，再形成诊断或修改方案。本文提供迁移后的工程方法；框架内部契约和命令以目标 checkout 为准。

## 按影响选择参考

- 训练、Checkpoint、并行策略、LoRA/量化或训练 Kernel：[训练验证](references/training.md)。
- Rollout、reward、权重同步与异步训练：[RL 边界](references/rl.md)。
- Serving、配置 API、调度、缓存及多阶段多模态：[推理验证](references/inference.md)。

只读相关章节，跨边界改动可组合。Kernel 计时、数值一致性和 profiler 诊断使用仓库已有专项 Skill，不在这里重写其方法。

## 工作方式

1. 写清变更契约：已有行为、目标行为、调用者、支持配置、可观察失败与不可改变的行为。需求不足以确定产品行为时请求必要澄清，继续可独立完成的调查；不机械要求每次任务新建 Issue。
2. 定位实际路径：模型与配置注册、backend 选择、依赖与编译产物、CI 选择器；确认实验未误走回退路径。尽量沿用目标项目接口，避免为了局部任务建立新的长期抽象。
3. 定义最低有效验证：将快速静态/CPU 检查、设备正确性、模型行为、分布式恢复和性能测量分开；选能暴露故障的最小规模，再按影响扩展。
4. 实施范围内的修改，同步公共配置、用户文档与必要生成产物。先检查生成器，不能手工修补生成结果。实验功能与稳定默认路径分开评审。
5. 在真实目标路径执行验证，保留 baseline/candidate、输入与配置。缺设备、权重或环境时说明未验证项，不用 mock 或导入成功代替设备证据。

## 报告

返回修改及原因、兼容范围、准确命令与完成结果、设备和拓扑、未执行项及原因。正确性和性能分别报告；修复提供前后失败对照，性能声明给绝对数据与波动。任务要求只读时只提供建议。

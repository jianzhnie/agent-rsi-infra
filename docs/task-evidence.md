# 任务契约与验证报告

先约定任务目标、目标 revision、允许修改与执行范围、验收条目和资源预算；执行后逐项补充结果。报告不授权运行命令，也不代替人工审查。

使用 JSON version 1：根字段为 `task_id`、`objective`、`revision` 和 `criteria`。每项 criterion 包含唯一 `id`、`expected` 和 `status`。状态只允许 passed、failed、not_run、not_applicable；执行项必须提供 evidence 对象（command、result、artifact），未执行或不适用项提供 reason。保留失败和未执行项，不从报告中删除。

运行 `python scripts/validate_task_result.py <report.json>` 检查结构。验证器不会执行命令、打开产物或证明证据真实性；人工需核对日志与实际代码版本。工作区未提交时记录基准 commit、diff 或源码 hash，不能仅以分支名代表候选。

训练性能任务可从[任务描述模板](templates/training-optimization-task.md)填写输入、授权和预算；模板不替代执行前固定的验收契约。

## 性能与环境

性能证据另行记录 baseline/candidate、模型与输入 revision、硬件数量和拓扑、驱动/runtime/compiler/framework 版本、dtype、shape、并发与并行配置、计时边界、缓存和 graph 模式、warmup、重复次数、原始样本及波动。禁止把 profiler 数据直接代替正式 benchmark。环境指纹只采集明确列出的非敏感字段，不保存全部环境变量或凭证。

性能记录字段的合成示例见 `tests/test_benchmark.py` 的 `sample()`，仅用于格式测试，不是硬件测量。运行 `python scripts/validate_benchmark.py <report.json>`，校验 latency 记录的单位、重复样本、版本及固定环境字段，输出 median、范围和环境 SHA-256。当前仅支持延迟，不将吞吐量倒数当加速比。环境 hash 表示字段一致性，不证明环境真实或完整；硬件证据仍需实际采集。

## Skill 回归与人工晋级

真实任务样例保存原始输入、失败证据、预期行为、允许操作、资源需求与评价方法；不把期望答案直接泄露给执行者。代码检查、脚本回归与 Agent 行为评测分别报告。尚未执行真实 Agent 对照时标记未验证，不以结构测试宣称 Skill 有效。

候选规则或 Skill 改进比较同一任务集的完成情况、正确性、时间/资源成本和退化项；同时记录根因分类，避免把环境或任务定义问题归因于 Skill。人类审查证据及适用范围后决定接受、继续试验、拒绝或回滚。晋级不自动修改规则或发布代码；只有候选量和跨项目汇总需求真实增长后，再考虑自动评估服务。先积累可复现样例，再评估基础设施。

## 固定验收与候选比较

执行前独立保存 contract：`task_id`、`objective` 和仅含 `id`、`expected` 的 criteria。执行报告不得省略或改写约定条目。契约文件由具体任务提供；当前仓库未提供可用的任务契约样例，真实任务还须记录授权范围、输入、资源和失败依据。

```bash
python scripts/validate_task_result.py result.json --contract contract.json
python scripts/compare_task_results.py contract.json baseline.json candidate.json
```

比较器要求两个结果分别匹配同一契约且 revision 不同，输出状态变化、原通过项的退化、候选失败及未验证项。合法比较返回成功仅表示格式与契约匹配，不表示候选通过验收。它不检验证据真实性、成本或统计显著性，也不会执行证明脚本、写回规则或晋级。

人工评审记录以下字段后再决定：候选与基准 revision、contract 及输入标识、比较结果与原始日志位置、正确性和性能变化、时间/费用/设备成本、适用范围、残余风险、审查人、日期、结论（接受/拒绝/继续试验）与理由。候选 failed 或 not_run 项不能靠省略或变成 not_applicable 消失；不适用需审查理由，必要时修订契约并重新比较双方。

当前已提供契约绑定与比较工具，尚无真实 Agent 候选晋级记录。结构和状态检查是人工评估的输入，不能伪装成人工批准。

## Validation Report 状态与模板

人工报告使用六种状态，避免把所有未执行情况合并为“跳过”：

| 状态 | 含义 | 当前 JSON v1 映射 |
| --- | --- | --- |
| passed | 已执行且达到预先约定的验收条件 | passed，附 evidence |
| failed | 已执行但未达到验收条件，包括运行失败 | failed，附 evidence |
| skipped | 适用，但按已约定的选择/预算策略主动跳过 | not_run，reason 写明 skipped 及策略依据 |
| blocked | 因依赖、设备、权限或输入缺失而无法执行 | not_run，reason 写明 blocked 及阻塞条件 |
| not_run | 适用但尚未执行，未归入前述两类 | not_run，附原因 |
| not_applicable | 不在本次变更的适用范围内 | not_applicable，附范围依据 |

JSON v1 不接受 skipped/blocked 字面值；检查编排器的结果 JSON 是另一协议，不能直接当作任务报告。映射只保持兼容，原始详细状态和原因必须在人工报告中保留；未执行不计为通过。

```markdown
# Validation Report
- 任务：<task_id、目标、契约位置、允许操作>
- 版本：<目标代码 revision/diff、Skill revision、客户端及精确版本>
- 环境：<OS、依赖、设备、输入版本；无设备任务注明不适用>

| 验收项 | 预期行为 | 状态 | 实际命令与结果 | 证据位置 / 原因 |
| --- | --- | --- | --- | --- |
| <固定 criterion id> | <执行前约定> | <六种状态之一> | <实际执行内容，未执行则注明> | <日志、原始样本，或未执行依据> |

- 总结：<通过、失败、跳过、阻塞、未运行、不适用分别计数>
- 限制与后续：<未覆盖范围、阻塞解除条件、失败处理>
- 人工审查：<审查人、日期、结论与依据；未审查则标记待审查>
```

模板不是执行记录，占位符不构成证据。Kernel 任务的输入与性能交付示例见 [Skill 使用样例](skill-examples.md#kernel-优化交付示例)。阶段交付与完成条件统一见 [RSI 路线图](RSI_DESIGN.md#9-落地路线图与验收标准)，本页建设状态表记录具体实现缺口，不另设一套阶段完成标准。

## 批量评测的结果管理

每次运行建立独立记录，每个评测项使用稳定标识并保存实际命令、代码/模型/输入 revision、环境、执行状态、原始结果位置和失败原因；多轮结果分别保留，注明样本数和汇总方法，不以首轮替代多轮统计。

单项失败后可继续资源与状态均独立的后续项，保留失败项及非成功的整体结论。共享环境损坏、设备故障或前置项失败影响后续可信度时停止受影响项并记为 blocked，不盲目继续。复跑关联原 run/item，保留原失败记录，不覆盖成一次成功。

smoke 与完整评测分别记录模式、数据子集、样本数及参数差异。smoke 仅证明所测范围可运行，不能更新正式完整评测基线或声称完整质量通过。批量执行结束报告成功、失败、阻塞和未运行项，并验证日志、原始结果与汇总一致；命令返回 0 不足以证明所有结果存在或满足验收。

规则提炼自 SGLang-Omni running-eval-suite，固定来源、许可与本地适配见[来源记录](../.agents/skills/code-reviewer/references/sglang-omni/UPSTREAM.md)。只采用结果管理方法，不迁入 runner、自动改表或自动提交；记录规范不授予启动评测、使用设备或发布结果的权限。
